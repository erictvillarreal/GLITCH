1 Executive Summary

1.1 What is GLITCH

GLITCH is a research program to systematically pass a Topstep futures prop-firm evaluation (the “Combine”) and then generate real payouts from the resulting funded account (the “XFA”). The project runs two parallel, independently-optimized tracks referred to throughout this report as Cerebro 1 and Cerebro 2.

Cerebro 1 — pass the Combine. Objective: maximize the probability of reaching the profit target within a bounded ~15-day evaluation window, where the maximum loss is capped at the fee of the attempt (~$49–149). This bounded-loss, bounded-time structure permits a strategy to pass reliably even without genuine predictive edge — convexity of the payout does the work, not market prediction.

Cerebro 2 — survive and generate payouts once funded. A fundamentally different problem: the horizon is unbounded, there is no profit target, and the relevant threshold is 5 winning days of ≥$150 net, not a lump-sum target. A strategy with zero or negative net edge that reliably passes the Combine does not survive Cerebro 2 — without the bounded window protecting it, the trailing loss limit (MLL) eventually catches any strategy without genuine positive edge.

1.5 Key Findings

Cerebro 1’s G2 candidate is real, reproducible, and does not depend on predictive signal. It exploits gambler’s-ruin geometry (SL/TP placement) within the Combine’s bounded-loss structure — validated against real MES price data with the triple-barrier ambiguous-bar bug fixed first (see Cerebro 1 Timeline).

Cerebro 2’s central structural finding: optimizing for the Combine and optimizing for XFA survival are not the same problem, and can actively conflict. The MGC/150K candidate — designed to tolerate very few consecutive losses once funded — has a Combine pass rate of only 47.5%, roughly half of G2’s 81.4%, when run through the exact same, already-audited Combine simulator. No Cerebro 2 candidate’s Combine pass rate should ever be assumed from another candidate’s number (see Cerebro 2 Timeline).

A vectorization bug turned a ~2-hour job into a projected ~70-hour one — caught before it ran unsupervised. An exhaustive Monte Carlo grid’s ETA climbed from an estimated 2 hours to a projected 70 hours after only 1% progress; the root cause was a scalar per-path Python loop whose cost varied ~75x across the parameter space. Vectorizing it (validated bit-exact against the old implementation across 32 cases before replacing it) cut the real run to 51 minutes (see Infrastructure & Operations).

A live production incident chain cost ~2.5 weeks and traced to five distinct, unrelated root causes — a requirements.txt file read from the wrong path by the actual build system in use (Railpack, not the Nixpacks config that was being edited), missing Telegram/Massive environment variables discovered one crash at a time, an ephemeral filesystem silently resetting all persistence between cron runs, and a Yahoo Finance data-availability gap at the market open (see Infrastructure & Operations).

A “10-minute” data delay claimed by a paid vendor was never verified — and a first attempt to verify it returned an impossible number, catching a second, unrelated API bug. A real-time delay probe for Massive’s futures data returned a 319,174-minute (7+ month) delay; the root cause was an unreliable API pagination pattern (sort=asc over a date range never returns the most recent record on this endpoint — confirmed with raw API evidence, not assumed) (see Infrastructure & Operations).
